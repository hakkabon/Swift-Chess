# Swift-Chess

A SwiftPM package that wraps the Rust chess engine (the `ChessEngineKit` FFI,
see the root `../README.md`) and ships a small macOS **SwiftUI** chess app on
top of it.

The Rust engine runs as a native library linked through an XCFramework; the
Swift side never re-implements chess rules — it only renders the board and
forwards moves and FENs across the FFI.

The FFI also exposes **PGN import/export** (`loadPgn`, `savePgn`, `getTag`,
`setTag`, `moves`); the bundled XCFramework was rebuilt from current Rust source
and includes them. These are optional — the app drive and can use them to
load/save games.

---

## Requirements

- **macOS 13** or later (declared in `Package.swift`).
- A **Swift 6.0** toolchain (Xcode 16+ or the standalone Swift 6 toolchain).
- The package currently builds an **x86_64** binary because the bundled
  XCFramework contains only the x86_64 slice, so on Apple Silicon it runs under
  Rosetta. (Add an `aarch64` slice to the framework for a native arm64 build —
  see the root README.)

> The package sets `swiftLanguageModes: [.v5]`. uniffi's generated bindings use
> some concurrency annotations that aren't fully Swift-6-clean, so the package
> is compiled in Swift 5 language mode even though it requires the Swift 6
> compiler. Do not switch this to `.v6` without also patching the generated
> bindings.

## Package layout

```
swift/
  Package.swift
  Frameworks/
    ChessEngineKitFFI.xcframework/     # binary target (Rust static lib + C header)
  Sources/
    ChessEngineKit/                   # generated by uniffi — do NOT edit by hand
      ChessEngineKit.swift
      ChessEngineKitFFI.h
      ChessEngineKitFFI.modulemap
    ChessUI/                          # the macOS app
      ChessUIApp.swift                # @main App entry point
      ContentView.swift               # board + side panel + promotion sheet
      BoardView.swift                 # 8x8 board rendering & click handling
      ChessViewModel.swift            # @MainActor ObservableObject around ChessGame
    ChessSmokeTest/                   # headless CLI that exercises the FFI
      main.swift
```

### Products

| Product | Kind | Purpose |
| --- | --- | --- |
| `ChessEngineKit` | library | The uniffi-generated Swift bindings + XCFramework. Import this to use the engine. |
| `ChessUI` | executable | The macOS SwiftUI chess application. |
| `ChessSmokeTest` | executable | A headless test that plays moves through the FFI and asserts engine sanity. |

## Building & running

```bash
cd swift

swift build                  # build everything
swift run ChessUI            # launch the macOS app
swift run ChessSmokeTest     # run the headless FFI smoke test
```

`ChessSmokeTest` prints the start position's legal-move count (should be **20**),
plays a few engine moves, and verifies each returned move is legal and that the
SAN strings are produced without error. It is the fastest way to confirm the
Rust/XCFramework/Swift pipeline is healthy after an engine change.

## How the app uses the engine

```
ChessViewModel (@MainActor, ObservableObject)
        │  owns a ChessGame (FFI object, thread-safe on the Rust side)
        ▼
   ChessGame  ──make_move / ai_move / legal_moves / get_state / get_cells──▶  Rust
```

- **`ChessViewModel`** holds a `ChessGame` instance and mirrors its state into
  `@Published` properties the views observe (`board`, `state`, `selected`,
  `legalTargets`, `moveHistory`, `thinking`, `gameOver`, etc.).
- **Board interaction** is driven by square indices. A tap resolves to a
  `(file, rank)` via `square = rank * 8 + file`, identical to the Rust
  convention. Selecting a piece shows its legal targets; tapping a target calls
  `make_move(from:to:promotion:)`.
- **AI moves** run off the main thread: `ChessViewModel` calls
  `game.aiMove(depth:)` inside a `Task.detached`, then publishes the new state.
  `aiMove` both computes *and applies* the move on the Rust side, so the view
  simply refreshes afterwards.
- **Promotion** is handled by `PromotionChooser` (a sheet) when a pawn reaches
  the last rank; it supplies the `promotion` argument to `make_move`.

### Coordinate mapping in the UI

`BoardView` renders the board with **rank 0 (White's back rank) at the bottom**,
matching the standard White-below orientation:

- A square index `sq` maps to `file = sq % 8`, `rank = sq / 8`.
- Pixel placement: `x = file * cell`, `y = (7 - rank) * cell` (so rank 0 is at
  the bottom).
- Click handling inverts this: `file = x / cell`, `rank = 7 - y / cell`.

The `board` dictionary is keyed by the same square index returned from
`get_cells()`, so rendering and input stay consistent.

## Updating the Rust engine

When the Rust code changes:

1. Rebuild the static library and overwrite the `.a` inside the XCFramework
   (see "Quick rebuild" in the root `../README.md`).
2. From this directory, force SwiftPM to relink:

   ```bash
   swift package reset && swift build
   ```

3. If you changed the **Rust FFI surface** (the `#[uniffi::export]` items in
   `src/lib.rs`), you must also regenerate `ChessEngineKit.swift` and
   `ChessEngineKitFFI.h` and copy them into `Sources/ChessEngineKit/`. The
   generated files there are produced by uniffi — edit the Rust, not the Swift.

## Troubleshooting

- **App won't launch on Apple Silicon / odd crashes after an engine change:**
  the XCFramework is x86_64-only and runs under Rosetta. After swapping the
  `.a`, always `swift package reset` so SwiftPM re-copies and re-links the
  framework; otherwise it keeps the previously linked (stale) binary.
- **`cannot find type 'PieceKind' / 'Side' in scope`:** make sure the file
  imports `ChessEngineKit`. The FFI types live in that module.
- **Build errors about concurrency / `Sending` / `async`:** do not flip
  `swiftLanguageModes` to `.v6` without adjusting the generated bindings.
- **`rustPanic` / `IllegalMove` from the engine:** the engine should never
  return an illegal move; if you see one, it is a bug in the Rust side — run
  `cargo test` in the root crate and report the failing case.
