# Swift-Chess

A SwiftPM package that wraps the Rust chess engine (the `ChessEngineKit` FFI,
see the root `../Chess-Engine/README.md`) and ships a **multiplatform**
SwiftUI chess app: a **macOS** app built by SwiftPM **and** an **iPadOS / iOS**
app built from an Xcode project in `iOSApp/`.

The Rust engine runs as a native library linked through an XCFramework that
contains **macOS (x86_64 + arm64)** and **iOS (arm64 device + arm64
simulator)** slices. The Swift side never re-implements chess rules — it only
renders the board and forwards moves and FENs across the FFI. The FFI also
exposes **PGN import/export**.

---

## Requirements

- **macOS 13** or later (for the macOS app) and **iOS 16** or later (for the
  iPad/iPhone app), both declared in `Package.swift`.
- A **Swift 6.0** toolchain (Xcode 16+ or the standalone Swift 6 toolchain) for
  the macOS app.
- **Xcode 16** to build/run the iPadOS/iOS app from `iOSApp/ChessUI.xcodeproj`.
- The package sets `swiftLanguageModes: [.v5]`. uniffi's generated bindings use
  some concurrency annotations that aren't fully Swift-6-clean, so the package
  is compiled in Swift 5 language mode even though it requires the Swift 6
  compiler. Do not switch this to `.v6` without also patching the generated
  bindings.

## Package layout

```
Swift-Chess/
  Package.swift
  Frameworks/
    ChessEngineKitFFI.xcframework/   # binary target (Rust static libs + C header, multi-platform)
  Sources/
    ChessEngineKit/                 # generated by uniffi — do NOT edit by hand
      ChessEngineKit.swift
      ChessEngineKitFFI.h
      ChessEngineKitFFI.modulemap
    SwiftChess/                     # thin facade that re-exports the engine API
      SwiftChess.swift              #   @_exported import ChessEngineKit
    ChessUIKit/                     # the shared SwiftUI app (macOS + iOS)
      ContentView.swift
      BoardView.swift
      ChessViewModel.swift
    ChessUI/                        # the macOS app entry point (@main)
      ChessUIMac.swift
  iOSApp/                          # the iPadOS / iOS Xcode project
    ChessUI.xcodeproj/
    ChessUI/
      ChessUIApp.swift              #   @main iOS App using ChessUIKit
  Tests/
    SwiftChessTests/
```

### Products

| Product | Kind | Purpose |
| --- | --- | --- |
| `SwiftChess` | library | Re-exports `ChessEngineKit` (the engine FFI). Import this to use the engine types. |
| `ChessUIKit` | library | The shared SwiftUI board, side panel, and `ContentView`. Used by both apps. |
| `ChessUI` | executable | The macOS SwiftUI chess application. |

The iPadOS/iOS app is **not** a SwiftPM product — it lives in the `iOSApp/`
Xcode project and depends on the `ChessUIKit` package product.

## Building & running

### macOS

```bash
swift build                  # build everything
swift run ChessUI            # launch the macOS app
```

### iPadOS / iOS

Open the Xcode project and run it on a device or the simulator:

```bash
open iOSApp/ChessUI.xcodeproj
```

The project references this package locally (`../`), so Xcode resolves
`ChessUIKit` (and transitively the Rust XCFramework) automatically. Pick an
iPad or iPhone destination and press Run. The simulator runs on Apple Silicon
Macs (no x86_64 iOS simulator slice is shipped).

## Features

- **Three game modes** (side-panel picker):
  - *Human vs Human* — both sides played on the board.
  - *Human vs AI* — play one side; choose White or Black; the engine replies.
  - *Computer vs Computer* — both sides are driven by the engine. The app steps
    through the whole game automatically (with a short pause between plies so
    you can watch), stopping at checkmate/stalemate/draw.
- **Three board sizes** (Small / Medium / Large) — a picker scales every square
  and piece glyph.
- **Crisp vector piece artwork** — black and white pieces are drawn directly
  from their matching PDFs in `Assets.xcassets`, using each asset's original
  colors and preserved vector representation.
- **Drag & drop** — grab a piece and drop it on a (legal) square to move it; tap
  selection still works as an alternative.
- **Optional coordinate labels** — toggle the file letters (`a`–`h`) along the
  bottom rank and the rank numbers (`1`–`8`) along the left file on or off.
- **Adjustable AI strength** — a depth slider (1–6) controls the search depth
  for every engine move.
- **PGN** — load and save games, and edit PGN tags, through the FFI.

### Coordinate mapping in the UI

`BoardView` renders the board with **rank 1 (White's back rank) at the bottom**,
matching the standard orientation:

- A square index `sq` maps to `file = sq % 8`, `rank = sq / 8`.
- Pixel placement: `x = file * cell`, `y = (7 - rank) * cell` (so rank 0 is at
  the bottom).
- Click handling inverts this: `file = x / cell`, `rank = 7 - y / cell`.

The `board` dictionary is keyed by the same square index returned from
`get_cells()`, so rendering and input stay consistent. With coordinates enabled,
the bottom row shows the file letters and the left column shows the rank
numbers as corner overlays.

## How the app uses the engine

```
ChessViewModel (@MainActor, ObservableObject)
        │  owns a ChessGame (FFI object, thread-safe on the Rust side)
        ▼
   ChessGame  ──make_move / ai_move / legal_moves / get_state / get_cells──▶  Rust
```

- **`ChessViewModel`** holds a `ChessGame` instance and mirrors its state into
  `@Published` properties the views observe (`board`, `state`, `selected`,
  `legalTargets`, `moveHistory`, `thinking`, `gameOver`, `mode`, `boardSize`,
  `showCoordinates`, etc.).
- **Board interaction** is driven by square indices. A tap resolves to a
  `(file, rank)` via `square = rank * 8 + file`, identical to the Rust
  convention. Selecting a piece shows its legal targets; tapping a target calls
  `make_move(from:to:promotion:)`.
- **AI moves** run off the main thread: `ChessViewModel` calls
  `game.aiMove(depth:)` inside a `Task.detached`, then publishes the new state.
  `aiMove` both computes *and applies* the move on the Rust side.
- **Computer vs Computer** repeatedly triggers `aiMove` for whichever side is to
  move; after each move it schedules the next, so the game plays to completion
  automatically. (The engine can also play both sides directly via
  `GameCore::self_play` on the Rust side — the app just drives `aiMove`.)
- **Promotion** is handled by `PromotionChooser` (a sheet) when a pawn reaches
  the last rank; it supplies the `promotion` argument to `make_move`.

## Updating the Rust engine

When the Rust code changes:

1. Rebuild the static libraries and the XCFramework (see "Cross-compiling the
   static library for Apple targets" in the root `../Chess-Engine/README.md`).
   The committed XCFramework already includes macOS + iOS slices.
2. From this directory, force SwiftPM to relink:

   ```bash
   swift package reset && swift build
   ```

3. If you changed the **Rust FFI surface** (the `#[uniffi::export]` items in
   `src/lib.rs`), you must also regenerate `ChessEngineKit.swift` and
   `ChessEngineKitFFI.h` and copy them into `Sources/ChessEngineKit/`. The
   generated files there are produced by uniffi — edit the Rust, not the Swift.

> The `update-swift.yml` workflow in the **Chess-Engine** repository
> automatically regenerates the bindings and the multi-platform XCFramework and
> pushes them here on every engine change, so most updates require only a
> `swift package reset && swift build` (macOS) or an Xcode rebuild (iOS).

## Troubleshooting

- **App won't launch on Apple Silicon / odd crashes after an engine change:**
  after swapping the static libraries in the XCFramework, always
  `swift package reset` so SwiftPM re-copies and re-links the framework;
  otherwise it keeps the previously linked (stale) binary.
- **iOS build fails with a missing `ChessEngineKitFFI` module:** make sure the
  XCFramework contains the iOS slices (rebuild per the root README). The iOS app
  only works on Apple Silicon simulators because no x86_64 iOS simulator slice
  is shipped.
- **`cannot find type 'PieceKind' / 'Side' in scope`:** make sure the file
  imports `ChessEngineKit`. The FFI types live in that module (re-exported by
  `SwiftChess`).
- **Build errors about concurrency / `Sending` / `async`:** do not flip
  `swiftLanguageModes` to `.v6` without adjusting the generated bindings.
- **`rustPanic` / `IllegalMove` from the engine:** the engine should never
  return an illegal move; if you see one, it is a bug in the Rust side — run
  `cargo test` in the root crate and report the failing case.
